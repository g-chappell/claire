# Architecture & State Management

- Require a single, canonical state machine with explicit phases (e.g., PLACEMENT → PLAYER_TURN → AI_TURN → GAME_OVER) and documented transition rules.
- Ensure the state machine enforces turn order (player shoots first) and blocks input during invalid phases (AI_TURN, GAME_OVER).
- Include state transition guards that validate preconditions before allowing phase changes.
- Require one authoritative module to own and expose the current game phase; all other modules must query this source, never cache phase locally.

# Shared Contracts & Constants

- Require a dedicated constants/types module as the single source of truth for all enums, grid dimensions, ship definitions, cell states, and timing values.
- Ensure no module redefines shared values (grid size, ship lengths, phase names) independently.
- Define cell state enums (EMPTY, SHIP, HIT, MISS) and shot result shapes ({hit: boolean, sunkShipName?: string, gameOver?: boolean, playerWon?: boolean}) in the shared module.
- Require all modules to import and reference these shared definitions; prohibit inline magic strings or numbers for game constants.

# Module Responsibilities & Boundaries

- Ensure the controller module owns game state, phase transitions, and win/loss logic; it must not perform rendering or direct DOM manipulation.
- Require grid/board modules to own only cell storage and mutation (place ship, record shot); they must not contain game-flow or turn logic.
- Ensure fleet/ship management (placement validation, sunk detection, fleet status) is isolated in a dedicated module; do not scatter ship logic across controller and board.
- Require AI modules to return target coordinates only; they must not mutate grid state or trigger UI updates directly.
- Ensure rendering modules are stateless and re-render purely from passed state; they must not cache game state or make decisions about game flow.
- Require input handler modules to translate DOM events into controller method calls without embedding game rules or state checks.

# Data Flow & Event Propagation

- Require a unidirectional data flow: input → controller → model update → state query → render.
- Ensure shot results (player and AI) follow identical pathways: controller receives coordinates, updates model, computes result, updates phase, triggers render.
- Require the controller to emit or return a consistent result object after every shot, containing hit status, sunk ship name (if applicable), and game-over flag.
- Avoid callback chains or event emitters unless explicitly documented as the architectural pattern; prefer synchronous method calls with return values.

# Cell & Ship Data Schema

- Define a standard cell data structure (e.g., {row: number, col: number, state: CellState, shipId?: string}) and enforce it across placement, hit detection, and rendering.
- Require shipId to be assigned during placement and used consistently for hit tracking and sunk detection.
- Ensure ship objects store positions as an array of cell coordinates and maintain hit tracking per cell index.
- Require the board module to expose a method that returns cell state by coordinate without exposing internal data structures.

# Placement & Validation

- Require placement validation logic (boundary checks, overlap detection) to be encapsulated in a dedicated validator module.
- Ensure the validator exposes a single method that accepts board state, ship definition, coordinates, and orientation, returning a boolean or error detail.
- Require random placement logic (for AI or auto-place) to use the same validator; do not duplicate validation rules.
- Ensure placement mode tracks current ship index and orientation state; this state must be reset on game restart.

# Reset & Initialization

- Require a first-class reset mechanism that reinitializes all stateful components: controller phase, both grids, AI memory, placement sequence, and UI overlays.
- Ensure reset returns the game to the initial placement phase without page reload.
- Require each stateful module to expose a reset or initialize method; the controller must call these in the correct order.
- Avoid implicit resets (e.g., recreating objects); make reset an explicit architectural operation with defined semantics.

# UI Rendering Contract

- Define a stable set of DOM element IDs and CSS state classes as the interface between logic and presentation.
- Require the renderer to map game state to CSS classes (e.g., phase → body class, cell state → cell class) using a documented mapping.
- Ensure the renderer exposes methods that accept state objects and update the DOM; it must not query game state directly.
- Require animations and visual feedback to be additive; the underlying DOM state (classes, attributes) must reflect the authoritative game state even if animations are disabled.
- Avoid using animation completion as a signal for state transitions; transitions must be driven by game logic, with animations as optional presentation.

# AI Player Architecture

- Require AI logic to be stateless per shot or to maintain only targeting memory (e.g., hunt mode coordinates).
- Ensure the AI module exposes a single method that accepts opponent board state (visible hits/misses only) and returns a coordinate.
- Require the AI to record shot results via a separate method; do not couple shot calculation with result handling.
- Ensure AI difficulty or strategy (random, hunt/target) is configurable via constructor or method parameter, not hardcoded.

# Inter-Module Communication

- Require explicit method signatures for all public module interfaces; avoid implicit contracts or undocumented side effects.
- Ensure shot result objects are passed as return values, not mutated in place or stored in shared global state.
